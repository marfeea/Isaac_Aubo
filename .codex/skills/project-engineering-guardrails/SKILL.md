# 项目工程修改规范

## 修改前检查

1. 在每次修改前运行 `git status --short`，并检查本次涉及文件的 `git diff`、未跟踪文件和当前内容。
2. 将已有工作区改动视为用户手动修改；不得覆盖、格式化掉或擅自回退。
3. 判断用户改动是否影响计划中的修改：
   - 无影响：继续，并避开无关改动。
   - 有影响但风险可控：调整实现以兼容用户改动，并在交付时说明。
   - 风险较高，可能破坏项目结构、模块边界、公共接口或运行行为：停止计划中的写入，向用户列出冲突、拟修改内容和风险，等待用户决定。
4. 若高风险在写入后才被发现，只撤销本轮由代理新增且能够明确识别的改动；不得使用 `git reset --hard`、`git checkout --` 等方式波及用户改动。

## 中文注释与编码

1. 本轮新增或改写的代码注释、文档字符串采用中文；保留必要的英文标识符、API 名称和原始报错文本。
2. 文件统一使用 UTF-8；修改已有文件时保持其换行风格，避免无关的整文件编码或换行转换。
3. 写入后检查中文文本能以 UTF-8 正常读取；发现乱码时先修复编码，再继续其他修改。
4. 不为显而易见的代码添加注释；注释应解释约束、原因、坐标系、单位、边界条件或非直观决策。

## 模块化与文件规模

1. 修改前统计涉及文件的行数，并识别其主要语义职责。
2. 文件超过 500 行或本次修改将使其超过 500 行时，主动检查是否混有明显不同的语义逻辑；若存在，将新逻辑或可安全迁移的独立逻辑拆到新模块。
3. 非必要情况下单文件不得超过 1000 行。只有在框架约束、强内聚生成代码或拆分会明显破坏可读性时才允许例外，并在交付时说明原因。
4. 拆分必须基于职责边界，不得只为减少行数机械切割；避免循环依赖、隐式全局状态和重复配置源。
5. 优先形成小而清晰的函数、类和模块，对外接口保持稳定；需要改变公共接口时先评估调用方。

## 四部分工程边界

按以下四类组织新增逻辑，并在修改时检查现有归属：

1. **可配置内容**：参数、资产路径、位姿、阈值、开关和环境配置。配置保持单一事实来源，不嵌入运行流程。
2. **逻辑脚本**：与具体 Isaac 控制器接口解耦的算法、状态处理、任务流程和通用工具。尽量使用可独立测试的输入输出。
3. **Isaac 控制器对接代码**：场景对象、传感器、动作、控制器和仿真生命周期适配。只承担框架交互及数据转换，不吸收通用业务逻辑。
4. **生成数据**：采集、整理、序列化、命名和输出路径管理。不得反向控制核心任务逻辑；输出格式和保存策略应可配置。

跨层修改时明确数据流和依赖方向。优先采用“配置 -> 逻辑 -> Isaac 适配/执行 -> 数据生成”的单向依赖；若现有目录命名与上述概念不完全一致，按职责判断，不为追求目录形式进行高风险搬迁。

## 日志与诊断代码

1. 错误栈、逐步打印、临时断言、截图和高频状态输出只作为研发诊断措施，不视为永久业务逻辑。
2. 在关键节点审查本次涉及区域的诊断代码：问题已定位、输出重复、默认高频打印或不再提供决策价值时，删除或降级为受配置开关控制的精简日志。
3. 保留能够定位启动失败、资源加载失败、控制器异常和数据写入失败的必要上下文；不得吞掉异常或删除关键错误信息。
4. 新增临时诊断时优先复用统一日志入口并提供关闭开关，避免散落 `print`、重复堆栈和每步无条件输出。
5. 清理范围限于本次修改相关模块；大范围日志清理若可能改变调试流程，先向用户说明风险。

## 实施与验证

1. 先确定最小改动面和所属工程部分，再实施修改。
2. 修改后再次查看 `git diff`，确认没有覆盖用户改动、没有乱码、没有意外的整文件换行变化。
3. 对编辑的 Python 文件至少运行语法编译检查；再按风险补充单元、导入或 Isaac 运行验证。
4. 交付时说明修改文件、模块归属、验证结果，以及因高风险而未执行的内容。
